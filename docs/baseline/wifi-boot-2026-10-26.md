# Wi-Fi at boot: where the six seconds go, and the DHCP ARP wait

The panel's Wi-Fi was connected about 6.56 s after reset (`boot_wifi_ms`, firmware `millis()`), stable over
43 retained boots since the SDIO reset-delay fix on 2026-10-25 (6,527–6,758 ms). The serial log of
2026-10-25 showed `Starting fast_connect (saved)` with the stored BSSID/channel and then about four silent
seconds until `Connected`. Opening USB serial restarts the panel and no cable was attached, so this work
measured over Wi-Fi only.

## Probe

`bench/wifi_boot.h` registers passive ESP-IDF event handlers after ESPHome's Wi-Fi setup (on_boot priority
249; the setup at 250 creates the event loop). It stores `millis()` once for `STA_CONNECTED` and
`STA_GOT_IP`, the negotiated auth mode and channel, and failed attempts before the first IP. `GET /status`
reports them as `boot_wifi_setup_ms`, `boot_wifi_assoc_ms`, `boot_wifi_ip_ms`, `boot_wifi_authmode`,
`boot_wifi_channel`, `boot_wifi_disconnects`, `boot_wifi_last_reason` and `boot_wifi_probe_error`.
`tests/test_wifi_boot.py` compiles the real header against stub IDF types.

Three OTA boots of the probe build, unchanged behaviour:

| Milestone | ms |
| --- | --- |
| Wi-Fi setup done (hosted link up, connect starts) | 2,322–2,323 |
| Associated (`STA_CONNECTED`) | 5,278–5,297 |
| IP (`STA_GOT_IP`) | 6,305–6,315 |
| ESPHome `on_connect` (`boot_wifi_ms`) | 6,560–6,566 |

The network is WPA2-PSK (auth mode 3) on channel 6, with no failed attempts. WPA3-SAE is therefore not the
cost. Because ESPHome already reuses the saved BSSID and channel, the connect is a single-channel fast scan,
so a full channel scan is not the cost either.

## DHCP: the ARP check

IP arrived a fixed ~1.0 s after association on every boot. ESP-IDF 5.5's default
`CONFIG_LWIP_DHCP_DOES_ARP_CHECK` probes the offered address twice before binding; its Kconfig help says this
"lasts 1 - 2 seconds". Only a device squatting on the router's own lease could answer it.

It is a Kconfig choice. `CONFIG_LWIP_DHCP_DOES_ARP_CHECK: n` in `sdkconfig_options` was silently ignored (the
built sdkconfig still had `=y`); `CONFIG_LWIP_DHCP_DOES_NOT_CHECK_OFFERED_IP: y` selects the no-check member.
A first candidate with only `CONFIG_LWIP_DHCP_RESTORE_LAST_IP: y` took effect but changed nothing
(IP at 6,310 ms, one boot) and was dropped.

Interleaved OTA boots of the two prebuilt binaries in one evening window, A = probe build with the ARP
check, B = the same plus no check, order ABABAB then BABABA. Median (min–max), n = 6 each, ms:

| Milestone | A (ARP check) | B (no check) |
| --- | --- | --- |
| IP after association | 1,008–1,094 | 13–241 |
| `boot_wifi_ms` | 6,590 (6,560–6,852) | 5,685 (5,553–5,941) |
| First background shown (`boot_bg_ms`) | 8,825 (8,775–9,982) | 7,959 (7,761–11,827) |
| All assets (`boot_ready_ms`) | 13,513 (13,150–16,362) | 12,606 (12,190–34,292) |

Every B boot reached Wi-Fi before every A boot. One B boot needed 34.3 s for all assets because the 857 KB orb
atlas took 34 s; its status showed no error counters (its API log was not captured; the second batch's
logs showed no download errors), and orb times varied widely in both variants
(A 9.2–13.9 s). The household Wi-Fi was congested during the whole window (Mac to router ping max
107–222 ms, LAN HTTP to Jarvis p95 142–288 ms). The sample cannot exclude that removing the one-second pause
before the first downloads makes such a stall more likely; it is the open question.

Raw status files, upload logs, API logs and scripts: `.panel-ci/wifi-boot-20261026/` (private).

## Installation status

The probe (variant A) is installed and committed. Variant B, without the ARP check, is **not installed**:
Joel dropped it on 2026-10-26 after the household Wi-Fi stayed too congested for the release gates (the
responsiveness gate's host round-trips failed for both candidates while the panel's own status time was
unchanged). To revisit it, set `CONFIG_LWIP_DHCP_DOES_NOT_CHECK_OFFERED_IP: "y"` in `board.py` and install only
through `tools/flash_panel.sh` on a calm network, then follow a few boots for the 34 s stall above.

**Correction (2026-10-26, later):** "congested household Wi-Fi" was the wrong diagnosis for the failed
host round-trips. The Mac was on 2.4 GHz channel 6, the same channel as the panel; on 5 GHz the Mac -> panel
ping fell from 90/245 ms to 5.7/13 ms (avg/max). Before revisiting variant B, run `tools/panel host-link`
and fix what it reports instead of waiting for a calm network. See
[responsiveness](../responsiveness.md#host-latency-failures-check-the-macs-link-first). The congestion
figures above are kept as measured; they were most likely measured over the same 2.4 GHz Mac link.

## What remains

About 3.0 s pass between the end of Wi-Fi setup and association on a known BSSID/channel with WPA2. That
happens inside the ESP32-C6 (esp-hosted slave: Wi-Fi start, probe, authentication, association, 4-way
handshake). The host has no further knob for it in ESPHome 2026.9.1; it needs C6-side logs or a debug slave
build. The ~250 ms from `STA_GOT_IP` to ESPHome's `on_connect` is ESPHome's own connection bookkeeping.

**Installed 2026-10-30.** Variant B is in `board_config/hardware.py` (asserted by `tests/test_panel_performance.py`)
and the built sdkconfig has `CONFIG_LWIP_DHCP_DOES_NOT_CHECK_OFFERED_IP=y`. `tools/panel host-link` was clean first
(router ping p95 4.8 ms). `tools/flash_panel.sh` passed all gates (build `24415186538f75ea8eabc530155e1dfc`). Its
first boot: associated 5,295 ms, IP 5,306 ms (11 ms later), `boot_wifi_ms` 5,522, `boot_bg_ms` 7,868,

## Before millis()

Every `boot_*_ms` counts from the panel's `millis()` 0, which is not the reset. `tools/panel boot-wall N`
(hold the device lock; each run restarts the panel) pings the panel every 100 ms through a software
restart and subtracts `boot_wifi_ip_ms` from the first reply after the reset. On 2026-10-30, ms:

| Build | Shutdown (restart request -> reset) | Reset -> `millis()` 0 | n |
| --- | --- | --- | --- |
| PSRAM memory test on (IDF default) | 490–514 | 2,029–2,081 | 3 |
| `CONFIG_SPIRAM_MEMTEST: n` | 491–498 | 1,310–1,388 | 4 |

The memory test wrote and read back all 32 MB before `app_main` and cost ~0.7 s on every boot; nothing
in `/status` showed it. The remaining ~1.3 s holds the bootloader's image check (0.34 s on the
2026-10-23 serial log) and the copy of the app to PSRAM (`CONFIG_SPIRAM_XIP_FROM_PSRAM`). The ESP32-C6 is
reset by esp-hosted's global constructor, after this window, so the whole Wi-Fi timeline moves with it.
The `millis()` milestones did not change (Wi-Fi setup 2,321, IP ~5,305, dashboard ~7,900).

The log ring (`tools/panel logs`, first lines of a boot) has one line per setup phase before the splash:
`Running through setup()` ~391 ms (all LVGL widgets are created before it), `Phase buses` ~399,
`Phase hardware` ~660 (display, codecs), `Phase before-lvgl` ~660, `Phase widgets-bound` ~929 (LVGL and
the other priority-400 components), then the splash render to `boot_ui_ms` ~1,034. The splash came at
~500 ms on 2026-10-25 and grew with the pages added since.
A later phase mark at priority 399 (`Phase after-lvgl-audio`) lands on the same millisecond as
`widgets-bound`: the ~270 ms between `before-lvgl` and the splash belong to the priority-400 components
(LVGL, I2S audio, the speaker media player, the microphone), not to the boot logo's binding at 394.

## Background decode, not the network

The same log showed the 770 kB `bg.qoi` taking 2.3 s (`Downloading image` 5,467 ms -> `boot_bg_ms` ~7,800)
while the orb atlas loaded 2.2 MB in 1.3 s beside it. Upstream's QOI decoder drew each of the 614,400
pixels through `ImageDecoder::draw` (float scale, two `ceil`) and a virtual `draw_pixel`. The local
`components/runtime_image` writes RGB565 directly at 1:1 scale (README there, `tests/test_qoi_rgb565.py`).
Installed 2026-10-30 (all gates passed), three `tools/panel boot-wall` restarts, ms:

| Milestone | Before | Direct RGB565 |
| --- | --- | --- |
| `boot_bg_ms` | 7,798–7,826 | 6,132–6,154 |
| `boot_shown_ms` (dashboard visible) | 7,884–7,907 | 6,216–6,236 |
| `boot_ready_ms` (all assets) | 12,114–12,202 | 7,556–7,611 |

Wi-Fi milestones were unchanged (IP ~5,305). One of the three runs gave `reset_to_millis0_ms` 2,179 against
1,328 and 1,371; the others and the four earlier runs agree on ~1.3 s, so it is most likely a late ping
reply, not a slower boot.

## Keeping the C6 running across a restart: rejected

esp-hosted can skip the C6 reset at host boot (`CONFIG_ESP_HOSTED_SLAVE_RESET_ONLY_IF_NECESSARY`: SDIO card
init first, reset only if it fails, host restart if no init event within 5 s). Installed by OTA on
2026-10-30 with the USB cable attached as a fallback, candidate `8e1bdb2f867665a8f3bc74f6010e73a3`: its log
ring stopped at `E (1090) H_API: ESP-Hosted link not yet up`, the task watchdog fired (reset reason 6) and
the bootloader rolled back to the previous build, which booted normally. The C6's own firmware (version
unknown) does not resume the link without a reset. Only a newer C6 slave firmware could change that.
`tests/test_panel_performance.py` keeps the option out. Capture: `.panel-ci/flash-logs/20261030-190941.*`.

## Audio after the splash: no effect

To move the ~270 ms priority-400 window out of the splash path, the I2S speaker and microphones and the
panel_audio microphone got `setup_priority: 389` (the mixer, resampler and speaker media player accept no
such option). Installed 2026-10-30 (all gates passed) and then reverted; three plus three
`tools/panel boot-wall` restarts of each gave the same numbers: window `before-lvgl` ~664 -> `after-lvgl-audio`
~980, `boot_ui_ms` 1,086–1,095, Wi-Fi setup 2,370–2,376, `boot_shown_ms` 6,445–6,716. The I2S setups are not
the cost; LVGL's setup and the speaker media player remain in the window.

The same window was ~930 and `boot_ui_ms` ~1,036 two hours earlier on the same source, and the orb atlas
load varied 1.3–5.7 s between boots in the same evening with a clean `tools/panel host-link`. Compare
candidates only within one session of interleaved boots; a later control can drift by 50 ms in setup and
by seconds in downloads.
