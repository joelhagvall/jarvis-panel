# Hallpanel project workflow

## Physical screen access

- Agents should use `tools/panel` as the stable entry point, not bare python3. It locates the repo/venv from any working directory. `tools/panel inspect` returns a fresh screenshot, widget tree and status in one private snapshot folder. See `docs/remote-panel.md`.
- For repeated operations, use `tools/panel session` with JSONL input/output or import `PanelClient(persistent=True)` from `tools/panel_remote.py`. Reuse the client instead of resolving/restarting for every action. Use `expect_page` guards for scripted navigation. The session stops on its first error; input is never retried after a disconnect.
- Use `tools/panel smoke --out /tmp/NEW-DIRECTORY` for the explicit free physical UI test. Scripts and protocol logic live in this repo; shared skills should point here rather than maintain copies.
- Use `tools/panel visual check` against the private `.panel-visual/reference-panel-v19/` (2026-11-03: Hemmet's house line last, Natt anchored on its full-screen tap); older references stay unchanged beside it. See `docs/visual-regression.md`. Never replace a reference merely to make a failed test green; inspect and explain the changes first.
- Inspect a fresh screenshot/UI tree before choosing coordinates. Test navigation through tabs/settings. Input runs the same real actions as a finger, so keep it within the user's task and restore settings changed by tests.
- The dedicated token is read from ignored `styles/glass-v2/secrets.yaml`. Never print it. Before audible/restart tests, read/save actual page/day-volume settings and their provenance. Preserve Joel's selected daytime volume; 20% is his night-mode preference, not a mandatory test level. Restore only test-owned values and preserve later user/HA changes (see docs/wakeups.md). No paid voice/model UI checks.
- Framebuffer screenshots do not establish physical flicker, backlight output or sound quality. Use them to assess rendered pixels and navigation without asking Joel to operate the screen.
- Never call a temporal symptom (blink, flicker, stutter) fixed from a still screenshot; report "installed, awaiting Joel's eyes". For an intermittent fault the verification must cover its period (a soak, `tools/panel sl-check`); one good sample is not "fixed".
- Night mode is no reason to postpone task-scoped gates. `tools/panel gates` leaves Natt with the real full-screen tap and puts the panel back with the Natt tab afterwards; it does not return by itself. After a manual upload at night, add `--restore-night`. Check `page_natt` before reporting a night run done.
- Parallel sessions share this checkout and the panel. Use `tools/panel lock status` or `tools/panel lock wait --max-wait S` instead of messaging another session. Do not edit, stage or commit another session's files. `deploy_jarvis.sh` ships them too, so first check that Jarvis already has them: `tools/jarvis_ssh.sh user@jarvis.local cat <installed path> | diff -q - <file>`.
- Never POST test prompts to the production Jarvis `/converse`: it writes Joel's real calendar, phone and history. Use `tests/integration_test.py --prompt` (docs/evals.md). Here "Sonnet", "Jarvis" or "hjärnan" means the live Jarvis brain (`tools/brain.sh`), not a model subagent.

## Validate and install

- Joel grants standing authorization for task-scoped panel restarts, firmware flashes and verification. Do not ask for another approval or a recovery-plan confirmation. Proceed through the checked harness. Generic speaker-click warnings are obsolete and must not be repeated. Keep identity, idle/lease, crash, bounded recovery and all release gates. A failure requires diagnosis; it does not authorize an unbounded retry. Git publication and paid model tests still require their own authorization.
- Responsiveness is a permanent release gate. Run `tools/panel responsiveness` before and after performance changes. Keep raw samples and compare the same protocol/policy with the measured `.panel-ci/baselines/responsiveness.json`. See `docs/responsiveness.md`. Report p50/p95/p99/max, frame pacing/jank and host latency separately. Never replace a failed baseline or discard slow samples. Software timing does not establish finger-to-photon latency.
- Measure observer overhead too. Keep on-demand UI diagnostics free of synchronous C6/Wi-Fi RPC calls on the LVGL task. Snapshot mutable UI data there and perform slow queries/formatting on a worker. The responsiveness baseline must exist and match the protocol/policy before normal installation.
- CI also records `tools/panel throughput`. Configured production 60 fps must pass its unchanged absolute limits and comparison with `.panel-ci/baselines/throughput.json`. The checked flash script requires this gate too. Retain all raw timings, actual source-change rate, observer/host latency and failed runs. The original-duration virtual-frame protocol differs from the older accelerated diagnostic. This measures the listening orb, not every screen or finger-to-photon latency.
- Run `.venv/bin/python tools/check.py` for free local tests and ESPHome configuration validation. After a YAML option change, `--config-only` validates the configuration in seconds; flash_panel.sh runs the full test suite before it.
- The public copy `jarvis-panel` is synced only with `tools/publish_public.py` (docs/public-export.md), never by pushing this repo's history there.
- Use `sh tools/deploy_jarvis.sh` for Jarvis deployment. It requires the local checks and candidate tests in Home Assistant before installation. It lists the uncommitted files it ships and restarts HA by itself only when files HA loads at startup differ on Jarvis (`ha/custom_components/jarvis_agent/`, the wakeup YAML); `--restart-ha` forces and `--no-restart-ha` prevents that. The script always restarts `hallpanel.service`. A firmware flash restarts the panel, never HA. Joel grants standing authorization to deploy Jarvis whenever a task needs it (2026-10-29: "du får deploya alltid sluta fråga mig"; again "du får, du får alltid ... sluta fråga mig om tillåtelse"): run the script yourself and report, never ask first. The same holds for starting, stopping and restarting Hallpanel's own `systemctl --user` units on Jarvis over `tools/jarvis_ssh.sh`. Only Claude Code's own permission check can still refuse it; then retry once citing this rule, and only if it refuses again give Joel `! sh tools/deploy_jarvis.sh`. Never route around the check.
- Before device work, use `tools/panel preflight`. USB requires an explicitly selected present port and checked serial/provenance, never a remembered or first-discovered ESP32.
- Use `sh tools/flash_panel.sh [DEVICE]` for panel firmware installation. It checks, builds, uploads and runs `tools/panel gates` in that order; do not pre-run `tools/check.py` before it. It fails in seconds when the device lock is held, stamps the firmware with CI's build id, records it and the shipped uncommitted files in `.panel-ci/last-flash.json`, and always ends with `FLASH OK` or `FLASH FAILED at <stage>`. Run the script itself as the background command so the task's exit code is the flash's. After a manual upload, run `tools/panel gates [--url http://IP:8080]` instead of retyping the chain. Report restart progress when relevant; omit the obsolete speaker-click warning.
- When a gate fails on host latency, run `tools/panel host-link` before blaming the network: a Mac on the panel's 2.4 GHz channel caused it on 2026-10-26 (docs/responsiveness.md). Never wait for a "calmer network".
- The external hallpanel skill's older `panel.sh flash` and direct ESPHome uploads bypass this repository's check. Prefer the checked script. If another upload path is necessary, run `tools/check.py` successfully first for that same candidate.
- A change Joel cannot see or hear (a log line, a comment, an internal check) waits for the next flash that brings something he asked for; never flash for it alone: every flash restarts the panel he is using (he stopped one, 2026-10-28).
- Fix failing/skipped tests or missing dependencies before installation. Do not add a skip-checks option to the installation scripts.

## Working style

- Log where it helps later debugging (Joel's rule, 2026-10-28): state changes, failures with their reason, retries, and a cheap periodic health sample of anything that can degrade silently. Journal or a bounded file under ~/.local/state, never secrets, and say in the owning doc where the log is and how to read it. No new pushes or alerts unasked.
- Do free, checked, reversible work that follows from the task without asking, then report. Ask only about paid work, secrets, deletion or product choices, and always with a recommendation.
- Open previews, videos and reports meant for Joel's eyes yourself (`open FILE`).
- The shell is zsh: quote globs (`--include='*.py'`, or use `rg`), never store a command line in a variable, never start a word with `=` (`echo ====` fails), and there is no `timeout` command on macOS. Targeted tests: `.venv/bin/python -m pytest tests/test_x.py` or `-m unittest tests.test_x`.

## Evals

- `tests/test_*.py` are the free checks. The release runner separates local tests from HA-runtime tests and rejects unexpected skips.
- `tests/integration_test.py --list` is a free preview. Real model evals require `--live --max-turns N` and are separate from release checks. Do not run paid evals just to verify the eval framework.
- `--max-turns` limits question turns, not dollars or model API requests. See `docs/evals.md` for isolation, reports and measurement limits.
- Turn a reproduced bug into a targeted free regression when practical. Avoid exact response wording checks for model evals.

## Maintain the harness when something is learned

- Every task that changed files ends with the shared `harness-retro` skill, unasked, and a `Harness:` line; its Stop hook sends the agent back once when the line is missing. Here a fix goes to the owning helper, a free regression in `tests/` and its canonical runbook, as below.
- For every code/config/tool change, check for a reproduced failure or disproved assumption. When one appears, fix the owning helper, add the smallest useful free regression and update its canonical runbook. Do not leave the lesson only in chat. No discovery means no new diary entry.
- Recheck assumptions from current output and keep claims within the tested method. Use [harness maintenance](docs/harness-maintenance.md) for the ownership map; do not copy tests, thresholds or instructions into parallel guides/skills/memory.
- Promote one-off scripts only for demonstrated reuse or a repeatable risk. Guard dependent actions with check=True/set -eu, preserve failed/slow evidence privately in .panel-ci, and merge superseded guidance when touching it.
- Use existing task authorization; this review alone grants no new paid/physical tests, background jobs or unrelated skill edits, and never weakens release gates. Report actual protections/verification when a new lesson changed them.
